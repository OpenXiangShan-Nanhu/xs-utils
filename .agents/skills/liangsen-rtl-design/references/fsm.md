# FSM 标准设计与审查

适用于控制器、协议引擎、流水控制、调度等状态机，不依赖某个具体模块。继承主规范的单次赋值、单驱动和循环规则。

## 1. 先选择控制模型

**只有执行路径明确、阶段互斥的控制才使用单一 FSM。** 明确路径可包含分支、等待和自环，不要求是单条直线；但独立事件可以并发或乱序完成时，不应通过增加组合状态强制它们按固定顺序执行。

| 控制特征 | 推荐组织 |
| --- | --- |
| 执行阶段互斥、转移路径明确 | one-hot FSM |
| 有明确主阶段，同时存在独立的并发/乱序条件 | FSM + 独立 flag |
| 没有必要的全局阶段，只依赖若干独立事实或就绪条件 | 纯 flag 控制 |
| 多条职责清晰、可独立推进的复杂路径 | 若干子 FSM + flag/握手协调 |

### Flag 生命周期与并发更新

- flag 表示可独立成立并保持的事实，例如 pending、received、completed 或 resource_valid；多个 flag 同时为 1 是合法并发，不对整组 flag 套用 FSM 的 one-hot 限制。
- 为每个 flag 定义复位值、置位事件、保持条件、消费/清零事件、取消或重新启动行为，防止遗留状态串入下一次操作。
- 同周期置位和清零的优先级必须按协议明确，用单个完整表达式或互斥分支更新一次；不同 flag 的独立事件可以同时提交，不用统一的 if/else 链丢弃其中一个。
- 对短脉冲事件，在实际接收时保存对应事实，消费前保持；不能因为主 FSM 尚未到达某个阶段就漏掉已接受的完成事件。
- 乱序完成按事务/槽位身份跟踪 flag 或 bitmap；同类多笔未完成操作不能用一个布尔位代替数量和身份，需要时用计数器、表或队列承载。
- 汇聚条件明确使用当前 flag 还是本周期更新后的结果，以及是否允许同周期完成；保持预期延迟，避免相互依赖的 next 逻辑形成组合环。

### 复杂 FSM 的拆分

- 当状态在枚举多个独立维度的笛卡尔积、条件跨职责耦合时，考虑按职责和独立路径拆成子 FSM，而不是不断追加全局状态。
- 子 FSM 各自拥有状态寄存器和局部 flag；上层只协调必要阶段，不直接写子 FSM 的内部状态。同一 flag 也只能有一个更新所有者。
- 明确子 FSM 的启动接受、完成保持/确认、忙闲、取消、错误传播和复位边界；用事件、握手或 flag 汇聚进度，不让多个子 FSM 组合次态相互等待。
- 分清层次调用与真正并行：拆分后仍需保留原有并发能力、背压、优先级和可见延迟，不能为了模块化引入意外串行化或死锁。

## 2. 先明确状态与时序契约

在改写前确认：状态集合和含义、初始/复位状态、转移条件、自环、并发事件优先级、每状态输出、Moore/Mealy 属性、输出是否寄存、非法状态处理。

- 用 `typedef enum logic [...]` 与具名状态；推荐 `state_q/state_d` 区分当前状态与次态，已有一致命名可保留。
- 使用符号状态，不靠裸数字、状态编码位运算或隐含赋值顺序表达转移。
- **推荐 one-hot 状态编码**：状态向量通常每个状态占一 bit，枚举值逐个置位，复位也进入合法的一热状态。二进制等其他编码仅在已有固定编码、面积或工具约束等理由明确时采用并说明。
- 若实现依赖 one-hot 位语义，确认综合编码设置和结果；不能只凭 RTL 枚举值假定工具不会重编码。每个独立子 FSM 分别检查 one-hot，不要求多个并行 FSM 的状态拼接后只有一个 1。
- 将协议事件定义清楚。例如完成转移若依赖握手，应检查实际接受事件而不只检查请求有效；不要擅自把示例中的 start/finish 当成通用协议。
- 多个事件竞争同一次状态转移时，在同一状态分支用显式 if/else 优先级表达；不靠多个独立 if 对 state_d 的后写覆盖。独立并发事实则分别更新 flag，不能因状态转移优先级而丢失。

## 3. 默认三段式

1. **状态寄存**：一个 `always_ff` 更新 `state_q`，使用非阻塞赋值；时钟、复位方式和复位状态遵守实际设计。
2. **次态逻辑**：一个 `always_comb` 由 `state_q` 和输入计算 `state_d`；每个状态分支完整赋值一次，保留自环。
3. **输出逻辑**：独立 `always_comb` 或简单连续表达式译码输出；不在这里更新状态寄存器。

禁止为省代码写 `state_d = state_q; case (...) ...` 或在 case 前设置输出默认值后覆写。状态保持应在各分支中显式表达，输出用完整分支或每个信号一个完整表达式。

数据寄存器、计数器与状态译码分离，以清晰的使能更新；不要把数据通路隐藏在状态编码中。确有必要采用不同组织时说明原因，不能改变延迟、复位或违反单次赋值。

## 4. One-hot Moore 示例

此例是路径明确的单任务控制，使用三 bit one-hot 状态和同步高有效复位；不规定其他模块的复位方式。start 在空闲状态被接受，finish 结束运行，完成状态保持到 ack；各状态均可自环。输出未额外寄存。并发或乱序任务不能直接套用该单任务流程，应先采用上述 flag 或子 FSM 建模。

```systemverilog
module fsm_example (
  input  wire  clk,
  input  wire  reset,
  input  wire  start,
  input  wire  finish,
  input  wire  ack,
  output logic ready,
  output logic busy,
  output logic done
);
  typedef enum logic [2:0] {
    ST_IDLE = 3'b001,
    ST_BUSY = 3'b010,
    ST_DONE = 3'b100
  } state_t;

  state_t state_q;
  state_t state_d;

  always_ff @(posedge clk) begin
    if (reset) state_q <= ST_IDLE;
    else       state_q <= state_d;
  end

  always_comb begin
    case (state_q)
      ST_IDLE: begin
        if (start) state_d = ST_BUSY;
        else       state_d = ST_IDLE;
      end
      ST_BUSY: begin
        if (finish) state_d = ST_DONE;
        else        state_d = ST_BUSY;
      end
      ST_DONE: begin
        if (ack) state_d = ST_IDLE;
        else     state_d = ST_DONE;
      end
      default: state_d = ST_IDLE;
    endcase
  end

  always_comb begin
    case (state_q)
      ST_IDLE: {ready, busy, done} = 3'b100;
      ST_BUSY: {ready, busy, done} = 3'b010;
      ST_DONE: {ready, busy, done} = 3'b001;
      default: {ready, busy, done} = 3'b000;
    endcase
  end
endmodule
```

各分支对 state_d、各输出 bit 分别赋值一次；状态寄存器的 reset/else 也是互斥的。组合逻辑不存在先默认赋值再覆盖。

## 5. 输出与复位语义

- Moore 输出基于当前状态；Mealy 输出可依赖输入，但必须明确组合路径、背压环风险与接口采样时刻。不要为了“标准模板”把两者相互替换。
- 基于 state_d 的输出不等价于基于 state_q 的输出；新增输出寄存器也可能增加一个周期。修改前核对波形与延迟。
- 需要寄存输出时，用明确的输出寄存器及其 next 逻辑，并验证是由当前状态还是转移事件决定；三段式本身不保证无毛刺输出。
- 明确 done 是单周期脉冲还是保持到握手的电平，明确进入/离开状态当周期的有效值。示例 done 为保持型，不可直接套用于脉冲接口。
- 复位极性、同步/异步、输出何时进入安全值及数据寄存器是否复位，按契约保持。异步输入或跨域事件需既有的 CDC 方案，不直接接入转移逻辑并假定安全。

## 6. 非法状态与未知值

- 次态 case 和输出 case 都提供明确 default，不产生锁存器；普通 `case` 为默认写法。
- 不用 `casex/casez` 通配符忽略状态未知位；不靠 full_case/parallel_case 或类似承诺隐藏缺失分支。使用 unique/priority 必须满足其真实条件，不能代替完整赋值或错误检测。
- default 的恢复目标和输出必须由安全策略决定：回到空闲、进入错误态或保持安全锁定均可能合理。示例回到 ST_IDLE 并非所有设计的要求。
- 安全 default 不应静默掩盖故障：验证中同时检测非法或未知状态；推荐的一热 FSM 在复位生效后检查 `$onehot(state_q)` 且状态不含未知位，不能用 `$onehot0` 放过全零。该检查逐 FSM 进行，不适用于允许多位同时有效的并发 flag。
- 若系统要求硬件级容错/非法状态恢复，验证综合后实现或对应工具约束；仅 RTL 中存在 default 不等于故障恢复结构一定被保留。

## 7. FSM / Flag 验证与审查清单

- 单一 FSM 是否确实对应明确、互斥的执行阶段？是否把并发/乱序条件误写成固定顺序或组合状态爆炸？
- 是否优先使用 one-hot？其他编码的理由与约束是否清楚？复位后全零、多热和未知状态是否被检测？
- 每个 flag 的所有者和生命周期是否明确？并发置位、乱序完成、同周期置位/清零、取消后重启是否会丢事件或误用旧状态？
- 子 FSM 是否各自独立拥有状态，通过明确握手协调？是否保留并行度，且没有循环等待、组合环或完成事件遗漏？

- 状态、次态和输出的驱动是否唯一？每个 case 分支是否完整赋值，是否仍有默认后覆盖或重复 bit 写入？
- 复位是否进入指定状态，输出是否在指定时刻安全？所有合法状态、自环和转移边是否覆盖？
- 多事件同周期的优先级、背压/等待、连续请求、最短/最长操作是否符合契约？
- 非法编码或未知状态的处理是否按策略生效，同时有诊断？故障注入需使用仿真/验证设施，不向可综合设计塞测试后门。
- 输出时序、done 脉冲/保持、握手接受次数是否一致？是否引入组合环或意外增加延迟？
- 在项目工具支持时加入状态合法性、转移条件、输出一致性和状态覆盖断言；活性/最终完成性质必须写清外部响应、公平性或超时假设，不能无条件承诺必然完成。
- 重构优先使用转移表、参考模型或旧实现做逐周期比对；明确没覆盖的参数、路径和工具限制。
